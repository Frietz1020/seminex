# Seminex API contract

This document describes the API contract exported by `src/api/client.ts`, the only data boundary imported by the UI. Supported authentication, identity, seminar, registration, attendance, webinar-proof, evaluation, certificate, and adviser-management operations use Supabase. Missing or partial public Supabase settings return `configuration_error`.

## Shared response and error shape

Every operation returns `ApiResult<T>`: success is `{ ok: true, data: T }`, with optional `fromCache: true` for a saved offline read; failure is `{ ok: false, error: { code } }`. Consumers should branch on `ok` and handle the stable error code.

`ApiErrorCode` contains these codes:

| Code | Meaning |
| --- | --- |
| `validation_failed` | A request failed validation. |
| `conflict` | A requested state change conflicts with current state. |
| `rate_limited` | The caller exceeded an operation limit, such as an OTP send limit. |
| `invalid_credentials` | Sign-in credentials or an OTP are not accepted. |
| `student_id_taken` | Sign-up cannot create an account for this Student ID. |
| `session_expired` | No usable session exists or the session expired. |
| `network` | A request could not reach the service. |
| `not_found` | The requested record does not exist or is not visible to this caller. |
| `seminar_full` | No registration slots remain. |
| `not_available` | The action is outside its allowed state or time window. |
| `forbidden` | The caller lacks the required role or organization access. |
| `configuration_error` | Required Supabase settings are missing or incomplete. |

`seminar_full` is the specific response for a full seminar.

## Roles

- **Public** means no signed-in account is required.
- **Student** means a participant or an org member using participant access.
- **Org user** means an active org member or the org's adviser.
- **Adviser** means an adviser account with access to the relevant organization.
- **Student account creation** means the public sign-up flow after OTP verification. The org sign-up wrapper creates the student account and then submits its organization request.

Supabase Auth manages its session in browser storage. UI components receive only safe identity fields through `api`; access tokens are not returned by the API. Database access is enforced by Row Level Security and server-controlled profile and organization membership records. Never expose a Supabase service-role key to the browser. Auth signup uses a six-digit email OTP sent to the Student ID-derived institutional address; sign-in does not use OTP. The app uses the Supabase browser client directly.

## Derived status and lifecycle rules

These rules are enforced by the client for display and by Supabase for state changes.

- Seminar lifecycle is upcoming before `startsAt`, ongoing from `startsAt` until the effective end, and finished at or after the effective end. For an org seminar ended early, the effective end is the earlier of `endsAt` and `endedEarlyAt`; cancellation is a separate org status.
- A finished student seminar remains on Home for less than one hour after `endsAt`. At the one-hour boundary it belongs in History. My Seminars follows the same selector, with evaluation-due seminars kept visible.
- Active slots count registrations whose status is `registered` or `confirmed`. Released and cancelled registrations do not count. There is a hard capacity limit and no waitlist.
- Confirmation defaults to opening 24 hours before the start and closing one hour before it. Opening hours-before must be greater than closing hours-before; closing must be at least one hour. Registration in the open window is immediately confirmed. An unconfirmed registration is released when the confirmation window closes, freeing its slot and removing its ticket.
- The attendance acknowledgement is prompted one hour before start for confirmed registrations. An unanswered prompt can appear again on a later app open. Cancelling remains possible until Time-In and requires a connection.
- Webinar attendance uses uploaded name-bearing image proof. Time-In proof is accepted during the seminar while no Time-In exists. Time-Out proof is accepted from 15 minutes before scheduled end through one hour after end, while no Time-Out exists. These offsets are configured in `src/config.ts`. The scanner is not used for webinars.
- Evaluation access and history certificate readiness use the seminar's own `requiredAttendancePercent`; there is no global attendance percentage in UI copy.
- Evaluation becomes due immediately when a registration has a validated Time-Out and meets that seminar's attendance threshold, including before its scheduled end. Once opened, it does not expire. Survey snapshots and responses are immutable; a changed published survey creates a new version, and organization analytics are calculated per version over all responses rather than the current page.
- Attendance QR data uses a short-lived, single-use challenge bound to the active registration and seminar. It must not contain Student ID or a permanent bearer token. Scanning is online only; printed ticket PDFs do not contain a scan QR.
- Seminar scan requests carry a unique idempotency key. The database locks the registration before choosing the next punch, writes the event with server time and authenticated officer, and appends to the ledger. The response includes the roster identity used for face checking.

## Confirmed business rules

- After an officer rejects webinar proof, the student may resubmit proof for that checkpoint until its upload window closes.
- An officer approves webinar proof only when the screenshot shows a name matching the student and visible webinar content.
- A rejected proof remains in the audit history. A new attempt is allowed for that checkpoint while its upload window remains open; a pending or approved proof blocks another attempt.
- Evaluation opens as soon as the student has a validated Time-Out and meets that seminar's attendance requirement. It stays open indefinitely.
- Attendance is calculated as: elapsed attendance is Time-Out minus Time-In; if Time-Out is absent, count from Time-In to current time capped at seminar end. Required minutes are the scheduled duration multiplied by that seminar's `requiredAttendancePercent` (60% by default), rounded up. Evaluation and certificate eligibility require a validated Time-Out.
- Academic-term labels are presentation-only and do not affect backend eligibility or position quotas.
- A certificate becomes ready as soon as validated Time-Out exists, the attendance requirement is met, and evaluation is submitted.
- If a student cancels and registers again, reactivate the same registration row, refresh its registration time, clear its prior confirmation and attendance-acknowledgement state, and recheck capacity and confirmation timing. The row stores current state; it does not preserve past cancellation cycles.

## Backend status and remaining work

### Implemented in the Supabase adapter

- Auth sessions and role/organization identity use Supabase Auth and server-controlled profile and membership rows. RLS and narrowly scoped functions guard organization access; service-role credentials stay out of browser code.
- Registration, cancellation, confirmation, capacity, and expired-registration release are database-backed.
- Attendance acknowledgement and scanner events use database functions and server time. Scanner writes are idempotent and require an active roster registration.
- Evaluation access is checked against validated Time-Out and the seminar's own attendance threshold. Published survey versions and submitted responses are immutable; organization responses are anonymized and paginated.
- Certificate eligibility, issuance records, serial assignment, and template snapshots are database-backed. The `issue-certificate` Edge Function renders PDFs into private Storage; eligible students and active organization members download through short-lived signed URLs. Certificate delivery is in-app only.
- Webinar proof uploads pass through an Edge Function, validate image type and size, and store objects privately. The retention period still needs a product decision.
- Auth OTP requests are implemented through Supabase Auth. Hosted delivery still requires a configured email provider; see [Environment and deployment guide](ENVIRONMENTS.md). This email is for sign-in and recovery codes, not certificate delivery.

### Remaining gaps and limits

- Adviser management supports adviser queues, directories, and member lifecycle changes. The certificate override request/decision flow is not connected: Supabase returns an empty `overrideRequests` array, and no Supabase submit/approve/deny operations exist.
- Adviser queues and directories currently return arrays rather than paginated results.
- Offline reads use the scoped caches described in the operation tables. Mutations are never queued.
